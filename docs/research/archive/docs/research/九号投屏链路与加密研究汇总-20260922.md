## 3. NinebotEnhance 项目定位

### 3.1 它做什么

NinebotEnhance 是运行在九号出行 App 作用域内的 LSPosed 模块，目标是把手机应用或录屏画面送到九号车辆仪表，并在画面上叠加手机状态、音乐、胎压、电压、速度、功率、通知和导航信息。项目 README 记录的已支持九号出行版本为 **6.10.10** 和 **6.10.11**。

项目已记录的显示/传输组合为：

| 仪表类型 | 分辨率/传输 | 当前证据 |
| --- | --- | --- |
| M5P 全彩屏 | 848×480，Wi-Fi Direct，H.264 | 已实测（项目自述） |
| 240×320 竖向半彩屏 | Bluetooth MPEG2 | 项目按配置适配，仍待对应实车验证 |

这张表说明的是 NinebotEnhance 的适配记录，不是所有车型的通用规格。

### 3.2 它不是什么

它不是：

- 独立连接车辆的通用投屏 SDK；
- 已公开的九号仪表 H.264/MPEG2 编码器；
- 可脱离九号出行 App 直接完成车辆认证和投屏的 BLE 客户端；
- Encryption3 的公开、完整实现。

项目使用九号自身的车辆数据接口，对车辆写入范围也有限；画面编码和发送仍由九号 App 的原生路径承担。因而“安装 NinebotEnhance”与“获得九号投屏协议栈”不是同一件事。

## 4. Shizuku/Root 投屏完整链路

NinebotEnhance 的逻辑链路可以概括为：

```text
九号设置/预览
  → 模块进程 FrameClient / Binder
  → Shizuku/Sui UserService 或 Root shell
  → 创建 VirtualDisplay
  → RGBA Surface
  → 九号 App 原生采集
  → 九号 App 编码器
  → WIFI / WIFI_KCP / BLE 发送器
  → 车辆仪表
```

关键边界：

1. **授权层**：Shizuku/Sui 或 Root 让辅助进程拥有创建独立虚拟屏的能力；系统录屏授权是另一条 `MediaProjection` 路径。
2. **采集层**：虚拟屏输出 RGBA Surface，模块把应用/导航画面放入该 Surface。
3. **编码层**：编码器和帧率/码率配置仍由九号 App 的原始发送链路处理。
4. **传输层**：按车辆配置选择 Wi-Fi RTP、Wi-Fi KCP 或 BLE RTP。
5. **车辆侧**：仪表接收并解码；车辆显示覆盖层可能在视频帧之后叠加，模块无法遮挡这些原车 Overlay。

所以，Shizuku 方案的价值是“把自定义画面接入九号 App 已有的采集入口”，不是“绕过九号 App 重新实现车辆协议”。

## 5. 九号出行 6.10.11 静态分析

### 5.1 配置读取和通道选择

`ScreenCastConfigClient.startReadFile()` 读取投屏配置文件；`ScreenCastDataSender` 按配置选择：

- `WIFI`
- `WIFI_KCP`
- `BLE`

相关证据：

- `tmp/decomp/ScreenCastConfigClient.java`（`startReadFile`）
- `tmp/decomp/ScreenCastDataSender.java`（通道分派）

这说明投屏并非固定走 BLE。最终通道由车型、仪表能力和九号 App 配置决定。

### 5.2 Wi-Fi RTP

`RtpSender` 的 Java 层行为显示：

- 视频数据按约 1400 字节分片；
- RTP payload type 为 32；
- 直接调用 `RTPSession.sendData()`。

在已查看的 Java 发送路径中没有发现对每个 RTP payload 先调用 AES 的证据。Wi-Fi Direct/WPA2 可能提供链路层保护，但这不能自动等同于应用层端到端 AES。

### 5.3 KCP

`WIFI_KCP` 使用 KCP 作为可靠传输/重传层。KCP 解决的是丢包、乱序和重传，不是加密算法；是否另有加密要看上层 payload 和 native 实现，不能因为出现 KCP 就判定“已加密”。

### 5.4 BLE RTP

Java 到 native 的调用链为：

```text
BluetoothRtpSender.send...
  → NBBleSender.sendRtp()
  → NbBluetoothDevice.writeRtp()
  → BleSdkClient.writeRtpData()
  → RustBridge.writeRtpData()
  → native Rust BLE SDK
```

相关证据文件：

- `tmp/decomp/BluetoothRtpSender.java`
- `tmp/decomp/NBBleSender.java`
- `tmp/decomp/NbBluetoothDevice.java`
- `tmp/decomp/BleSdkClient.java`

这条链路证明 BLE RTP 不是纯 Java 自定义写特征，而是交给九号的 native BLE SDK；它没有单独证明视频 RTP 的加密格式。

## 6. Encryption2、Encryption3、AA55 与 RTP 的关系

### 6.1 九号 App 内部的协议选择

`NbBluetoothDevice` 中可见：

- `BleEncryption3Protocol2` → `BleSdkEncryption3Processor`
- `BleEncryption2Protocol` → `BleSdkEncryption2Processor`
- 当设备的 `encryptProtocolVersion == 3` 时，会判定支持 V3Auth。

本地 native 库还出现以下可见符号/字符串：

- `crypto_encrypt`、`crypto_decrypt`
- `crypto_start_sn`、`crypto_setAuthParam`
- `Protocol::V3_2`
- `session_key_hex`
- `RtpHandler`
- `InvalidCiphertextLength`
- `RustBridge_writeRtpData`

这些证据足以说明九号的 native SDK 具备 Encryption3、会话密钥、加解密和 RTP 处理能力；但仅凭符号和静态调用关系，不能证明每个 RTP 视频包都经过 `crypto_encrypt`。

### 6.2 Codeberg `segway-ninebot-ble` 的确认范围

开源项目对 Encryption2 的实现相对完整，包含：

- `PRE_COMM`；
- `SET_PWD`；
- `AUTH`；
- AES、SHA-1、SN counter；
- 认证后寄存器读写的状态化加密上下文。

但该项目对 Encryption3/V3Auth 没有公开足够完整的 challenge、证书、密钥派生和状态机实现。远端协议说明把 Encryption3 描述为 **Protocol2 + V3Auth**，BLE 仍使用 `5A A5`；`5A B5` 更接近 Wi-Fi v2，不应直接当作 BLE Encryption3。

### 6.3 “AA 55”不能直接当成统一投屏头

对话中提到的 `AA 55` 需要与具体抓包方向、协议层和车型绑定：

- Codeberg BLE 文档/实现使用的是 `5A A5`（以及存在冲突的 `5A B5` 代际命名）；
- 九号视频路径的 Java 层表现为 RTP 分片、KCP 或 native BLE RTP；
- 因此不能仅凭一个 `AA 55` 头，就断定它是所有全彩/半彩投屏视频帧的统一外层格式或 AES 帧头。

如果已有项目对 `AA 55` 做了解析，应把它标记为“某一设备/某一层的抓包格式”，再通过方向、长度、计数器、明文边界和车型实测确认其与 `5A A5`、RTP 或仪表控制帧的关系。

### 6.4 当前可下的安全结论

| 层级 | 当前判断 | 依据/限制 |
| --- | --- | --- |
| BLE 认证、读取投屏配置 | 已确认使用 Encryption2 或 Encryption3 能力 | Java 选择器和 native 加密符号 |
| BLE RTP | 经 native Rust SDK，存在加密能力；是否逐包 AES 未完全确认 | 有 `writeRtpData`/`RtpHandler`，无逐包动态证据 |
| Wi-Fi RTP | Java 层未发现逐包 AES；可能依赖 Wi-Fi Direct/WPA2 或另有 native 保护 | 需要 pcap 和 native 运行时跟踪 |
| KCP | 可靠传输，不等于加密 | 协议职责不同 |
| 全彩/半彩差异 | 当前未发现按“屏幕颜色”单独分支加密；更像按通道/设备能力选择 | 仍需车型实测 |

## 7. 全彩屏与半彩屏：现有证据能否证明都加密？

不能证明“都加密”，也不能证明“都明文”。目前合理的分层判断是：

1. 全彩屏 M5P 的已知链路是 Wi-Fi Direct + H.264。Wi-Fi 关联本身可以有链路保护，但静态 Java 代码没有证明 RTP payload 采用九号 AES。
2. 240×320 半彩屏的项目记录是 Bluetooth MPEG2，具体车型仍待实车。它更可能进入 BLE native RTP 路径，因而会经过 BLE 会话/认证上下文；但仍不能从认证加密直接推出视频逐包加密。
3. 九号 App 共用 `ScreenCastDataSender` 和 native BLE SDK；当前没有证据表明“全彩屏关闭加密、半彩屏开启加密”，或相反。决定因素更可能是设备能力、投屏配置和所选承载网络。

工程上应把“认证/配置加密”和“媒体负载加密”分成两个布尔能力，不要在协议模型中用一个 `encrypted=true` 混合表示。

## 8. 不依赖九号 App 的实现路线评估

### 8.1 方案 A：继续挂接九号 App（短期可行）

适合快速验证自定义数据和 UI：

优点是协议风险最低，缺点是依赖九号 App 版本、Hook 签名、LSPosed/Root 环境和九号官方链路。

### 8.2 方案 B：从九号 App 提取 native 编码/发送器（不推荐作为第一步）

可以研究 native FFI 和调用参数，但会遇到：

- ABI、JNI、设备配置和版本门禁耦合；
- Encryption3/V3Auth 的关键状态可能只在运行时生成；
- 版权/许可证和九号 App 更新导致的兼容性风险；
- 没有实车时无法确认发送器的实际输出。

### 8.3 方案 C：独立 BLE 投屏客户端（长期目标）

需要分别实现并验证：

1. 车辆发现、服务/特征选择和分片；
2. Encryption2；
3. 目标车型的 Encryption3/V3Auth；
4. 投屏能力/配置读取；
5. 视频编码（例如 H.264 或 MPEG2）及 RTP/设备分片；
6. 车辆侧会话保持、计数器、重连和停止流程。

Codeberg 项目可以作为 Encryption2 和普通 BLE 设备层的参考，但不能把它的 Gen3/`5A B5` 常量直接当成目标车型的 BLE Encryption3 实现。

### 8.4 方案 D：独立 Wi-Fi 投屏客户端

如果目标车型确实使用 Wi-Fi Direct，需要额外获得：

- Wi-Fi Direct 建链/配对流程；
- 投屏服务发现和配置文件格式；
- RTP payload、时序、分辨率和关键帧策略；
- 是否有应用层加密、密钥从何处来；
- 仪表的停止/重连和错误响应。

只解析 `RtpSender` 的 Java 分片不足以实现完整客户端。

## 10. 后续动态验证计划（需要授权实车）

### 10.1 采集矩阵

至少按以下维度各采一次：

| 维度 | 采样项 |
| --- | --- |
| 仪表 | 目标全彩、目标半彩；记录型号、分辨率、固件 |
| 承载 | BLE、Wi-Fi Direct、KCP（若配置存在） |
| 状态 | 首次配对、已认证重连、开始投屏、停止投屏、异常重连 |
| 画面 | 静止纯色、变化画面、关键帧、不同分辨率/码率 |
| 日志 | logcat、九号 App 统计、BLE HCI、Wi-Fi pcap、时间戳 |

### 10.2 重点验证问题

1. `ScreenCastConfigClient` 返回的通道、屏幕尺寸、编码格式和加密字段是什么。
2. BLE `writeRtpData` 前后 payload 是否发生长度、计数器或密文变化。
3. native `crypto_encrypt` 是否位于 RTP handler 的每包路径，还是只服务认证/控制帧。
4. Wi-Fi RTP 是否包含可重复的应用层密文头、nonce、tag 或仅有普通 RTP。
5. 全彩与半彩是否仅切换编码/承载，还是同时切换会话加密策略。
6. `AA 55`、`5A A5`、RTP 外壳和仪表控制帧之间的层级关系。

### 10.3 动态手段和验收证据

在拥有设备所有者授权的测试环境中，可以使用 root 下的日志、进程跟踪、JNI/native 函数观测和 BLE/Wi-Fi 抓包进行交叉验证。验收至少需要：

- 一份可复现的原始抓包；
- 同一时刻的 App/native 日志；
- 明文配置/编码参数与线上的帧一一对应；
- 对重连、计数器回退、停止和错误路径的记录；
- 不把账号、密码、ADB 地址、会话令牌或个人数据提交到仓库。

## 12. 版本化结论

截至 2026-09-22，本研究的工程结论是：

> **NinebotEnhance 已证明“可以借助九号 App 的现有编码/发送链路，把自定义画面送到部分九号仪表”；它没有证明“已经拥有独立的九号仪表编码器或完整 Encryption3 投屏协议”。BLE 的 Encryption2/Encryption3 能力、Wi-Fi/KCP 传输和全彩/半彩适配必须分层描述；在取得目标车型实车抓包之前，不把视频 RTP 逐包 AES 和 `AA 55` 通用帧格式写成确定事实。**
