# 九号 5 英寸 BLE 开屏指令与投屏顺序

2026-11-20 续研。用户反馈：5 英寸仪表须先由官方 App 请求开启投屏，随后才能由独立发送器投屏；研究范围为所有 5 英寸车型的公共流程。官方静态输入仍为九号出行 6.10.11。没有连接的 ADB 设备，本轮没有无线抓包或实车出图验收。

## 指令与证据

官方 `DashNaviDataMessenger$Companion$start$2` 在已连接车辆上调用 `sendCommand("setNaviStart", [type.value], true, callback)`。`ScreenCastType` 定义 01=SimpleNavi、02=MapNavi、03=Cruise，停止写 00；`ScreenCastHelper` 默认 MapNavi。上层还有车辆能力与发动机状态判断，部分能力分支会回落 SimpleNavi，因此不能据此认定所有五寸都固定发送 02。

已经恢复的 Mmax2 / 14101、N3 / 14357、Mz / 14360 车型表一致：

| 字段 | 值 |
| --- | --- |
| 目标板 | TFT / `0x23` |
| 请求与响应命令 | `0x71` |
| 索引 | `0x00` |
| 地图投屏请求载荷 | `02` |
| 停止载荷 | `00` |

Gen2 地图投屏明文示意为 `5A A5 01 3E 23 71 00 02`。这是协议加密前的应用帧，不能直接当作 GATT 写入字节；真实报文使用该车已认证会话的密钥、计数器及校验。Gen3 也必须走自己的认证与加密，不存在跨车通用的固定密文。

## 找到的实现缺口与修正

独立测试包的默认 Wi-Fi 直连入口明确依赖仪表已由外部开启；官方 BLE 入口原来也在 `prepareMedia` 内先等 P2P 就绪，再执行 native `start_cast` 发模式请求。若仪表须收到 BLE 模式请求才开放 Wi-Fi，这个顺序无法启动。

本次复用既有会话、认证、配置、加密和 P2P 层，仅拆分控制与媒体就绪阶段：

1. 导入匹配车辆资料，扫描、连接、认证，读取并校验仪表配置。
2. 在“蓝牙开启投屏 → Wi-Fi”入口点击“蓝牙开启仪表投屏”，通过现有 `start_cast` 发模式请求。
3. 收到匹配的 TFT 模式响应，进入 `cast_mode_ready`；此时没有 UDP 心跳、KCP 或编码画面源。
4. 发现、选择并连接 Wi-Fi Direct；保留完整目标与组主、接口和 IPv4 核验。
5. 路由核验通过后执行 `start_wifi_media`，进入 `casting_ready` 才启动画面源，不再重复写模式 02。

停止及迟到响应继续经过原事务逻辑。Android 的 `nativeStage` 单独保存协议状态，避免“正在发现/连接 Wi-Fi”提示覆盖模式应答状态。半彩 BLE 与外部已开屏 Pro 直连仍分别使用原来的媒介和入口。

## “全部五寸”的边界

上述顺序是公共链路修正，不是所有五寸车型兼容性声明。尺寸不能决定认证代际、TFT 命令地址、导航模式、H.264 参数或 UDP/KCP。当前 BLE 准备与控制白名单仍只有 14101/14357/14360；未知车型保留诊断，不猜写地址。仪表参数仍从校验后的配置取得，未固定所有五寸为 848×480 或某种加密协议。

真正覆盖其他五寸车型，需要恢复各车型的命令和能力表，并以官方 App 开启投屏前后的 BLE 记录核对开屏、回应、Wi-Fi 出现的时间关系。没有手机、目标车型资料和车端响应时，不能认定所有五寸都已能脱离官方 App 开屏。

验证结果和运行日志位于 [本轮证据目录]（本地来源，未随附原始材料）。验证状态以该目录的 `verification.json` 为准；本地协议测试和构建不代表实际仪表已显示。
